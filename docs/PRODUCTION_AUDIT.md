# Production launch audit — 2026-11-05

Scope: existing Python/SQLite MVP, local live checks and prepared Ubuntu deployment.
No agent, new source, host provisioning or remote infrastructure changes.
Initial baseline: 157 tests passed. Findings below distinguish observed behaviour
from target-host assumptions. Deployment instructions: `PRODUCTION_RUNBOOK.md`.
Final verification: **174 tests passed**, both in the working project and in a
separate publishable copy using the blank profile template; Ruff, shell syntax
and diff whitespace checks passed. Ubuntu/systemd execution remains untested.

## Three highest-priority findings at entry

1. Daily notification identity was chat+day only. Every next day selected the same
   unresolved vacancies again. Fixed with additive per-chat native/semantic alert
   reservations linked to the durable outbox; same-day payload remains immutable.
2. Production service did not enable scoring; SDK defaults had no explicit output
   or input payload bound. Raw scoring/drafting exception strings could expose
   request content. Working-hours uncertainty had no separate review field.
   Fixed request bounds, safe errors, score failure states/retry cooldown and
   separate hours evidence. No drafts are required or generated by `daily`.
3. Unattended hosting was an example, not an installed service. Token refresh,
   writable state paths, callbacks and recovery required a concrete runbook.
   Units and configurable bounded launcher are prepared. Deployment is still
   pending approval and actual Ubuntu verification.

## What already worked and was retained

- Independent LinkedIn/karriere public searches with Playwright/HTTP, bounded pages,
  details, repeat detection and typed blocked/partial outcomes. Login-wall bypass
  and automatic login are not implemented.
- Versioned rules, lifecycle-aware canonical selection, full/snippet confidence,

- Daily outbox, safe Telegram transport error labels, callback offsets, SQLite WAL,

Legacy email-only `run` and `telegram-send` remain available but are not the chosen
production path. Do not schedule them alongside `daily`: they have separate
notification behavior and the old send-then-save path can duplicate after a crash.
The new daily path consults acknowledged legacy deliveries; the reverse path is
not a cross-scheduler duplicate guarantee. No architecture rewrite was attempted.

## LLM reliability and costs

The existing `gpt-5.4-nano` remains selectable. Current official documentation lists
$0.20 per million input tokens and $1.25 per million output tokens, and marks the
model page deprecated. The configured alias did work in this account during the
smoke test. Future availability is not assumed.
[Official model/pricing page](https://developers.openai.com/api/docs/models/gpt-5.4-nano).

Structured Pydantic output validates score/recommendation/confidence. Incomplete
requirements force provisional=true and low confidence locally. Prompt v3 makes
hours separate, treats vacancy text as untrusted, and avoids candidate contact
information in output. Cache version changes intentionally invalidate old prompt
results but preserve historical rows.

Default explicit request bounds: timeout 30s, zero SDK retries, 1,200 output tokens,
48,000 UTF-8 payload bytes. Production launch default: 5 candidate attempts/run,
configurable 0–25. Oversize/malformed/failed responses remain failed and visible;
there is no unlimited retry loop or drafting cost in daily. Successful-response
usage is counted. Errors without usage can incur unreported charges, so the
estimate is not a billing guarantee or dollar ceiling. No live failures were
forced against the paid API.

## Assumptions and outstanding launch gates

- No Ubuntu host has been selected/accessed or modified. Python 3.12 dependencies,
  Chromium OS libraries, board access from that IP, systemd verify/runtime,
  persistent disk permissions and reboot/catch-up need verification there.
- Configured credentials working on macOS do not prove indefinite unattended
  OAuth refresh or target-host API availability. Use the verified token privately.
- Telegram API acknowledgement proves remote acceptance, not that a human read it.
  No live button press was fabricated. Callback idempotence is covered by tests.
- A complete all-source local collection, real scoring, real Telegram delivery and
  restart replay have each been observed; a single all-source+AI run on the final
  host, scheduled operation and seven consecutive days have not.
- Off-host backup automation and independent dead-man monitoring are not installed.
  These limitations must remain visible at handoff.
